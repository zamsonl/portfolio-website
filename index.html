A C2 framework I wrote

I built my own command-and-control framework in Python rather than picking one off the shelf, so I know exactly what it does on the wire and on the host. The operator console has its own commands — list the agents that have checked in, open a shell, pull a file, run a recursive scan for interesting files.

I ran it only in an isolated lab, with authorization, to see what my detections would actually catch. Running the listener behind a tunnel and then hunting the same traffic from the SIEM is where my beacon rules came from.

The rule it produced

Watching that beacon arrive in Wazuh is how I wrote the detection for it. One rule notices a single outbound connection to the tunnel edge. A second says that six of them in a minute from the same machine is a pattern, not a coincidence.

I mapped it to the ATT&CK techniques for a command-and-control channel over a web protocol, so it lines up with the rest of the coverage.

The first rule alone is noise. The frequency rule is the one that means something.

c2_beacon.xml Wazuh rules I wrote for the C2 exercise 
<!-- one connection to a tunnel edge -->
<rule id="100001" level="3">
  <if_sid>81633</if_sid>
  <!-- edge ranges removed -->
  <field name="data.dstip">^(EDGE_RANGES)</field>
  <field name="data.dstport">^443$</field>
  <description>Outbound SSL to a tunnel edge</description>
</rule>

<!-- 6 in 60s from one host = a beacon -->
<rule id="100002" level="12" frequency="6" timeframe="60">
  <if_matched_sid>100001</if_matched_sid>
  <same_field>data.srcip</same_field>
  <description>Potential beacon: repeated outbound SSL</description>
  <mitre>
    <id>T1071.001</id>
    <id>T1572</id>
  </mitre>
</rule>

Samples, and what they showed

Each one follows the same path: I run it as the attacker, watch what the sensors see, and turn the gap into a rule. Red is what I did, blue is what the defence recorded, purple is what came out of it.

Ransomware behaviour, in Rust

AttackerMITRE T1486

I ran

A Rust sample that behaves like ransomware, hard-guarded so it could only ever write inside one canary folder. Benign by construction, never a live sample on the network.

The SIEM saw

File integrity monitoring caught the burst of changes inside the canary folder, which is what I wanted to confirm before relying on it.

I wrote

File integrity rules on that folder, mapped to T1486. My first version fired on every agent’s overnight scan, a domain controller included, until I scoped it to one path.

A C2 client, in C++

AttackerNetwork

I ran

A C2 client that checks in on a fixed interval, talking back to the listener in my own framework, reached through a tunnelling service so the traffic looked ordinary from outside.

The SIEM saw

Only DNS named the affected hosts. The firewall and the tunnel both reported a single shared address, which tells you nothing about which machine to check.

I wrote

The two beacon rules above, built on the DNS side rather than the firewall side, because that was the side with the answer.

Credential theft, macros and DLL injection

AttackerRules

I ran

A browser credential stealer in Python, plus Word macro abuse and DLL injection. Separately I ran phishing kits in the lab to watch exactly what they capture and where they try to send it.

The SIEM saw

These run and stay on the host, so the endpoint agent is where they show up, not the network sensors. That is the difference between a host rule and a network rule.

I wrote

Host rules for the behaviour that held up across samples, not the details that only matched one of them.

Built and ran a SOC

Network & Security Administrator intern, Palmgold Management Sdn Bhd, May to August 2026. The company had been hit by ransomware in August 2025 and still had no monitoring nine months later, when I started. I proposed a SOC, the head of IT approved it, and I built it and ran it until the internship ended.

It started as a proof of concept on a spare desktop and ended up as the system the company used. I was the only person on security, so the design, the rules, the incident response and the reporting were all mine. Most of the work was getting usable data in: Wazuh and OpenSearch on a Proxmox host I set up in the office, the firewall and wireless over syslog, agents on the Windows machines, and SPAN feeds from the core and access switches so the sensor sees the network instead of a slice of it.

  • Wazuh agents to more than 80 domain-joined Windows machines through Group Policy, with an installer that was safe to run twice.
  • Rewrote the Zeek decoders so each log type is identified by the fields only it has, and added detections for DGA bursts, DNS tunnelling, exfiltration and inbound scans.
  • Found that Zeek alerts were being written to disk and never indexed, because a field was hitting a keyword mapping while the bulk request still reported success. Fixed it with an ingest pipeline.
  • Recovered a full outage after archive logging filled the disk and every index went read-only, then set retention policies so it couldn’t happen again.

An alerting bot I wrote

Nobody was going to sit and watch a dashboard all day, so I wrote a bot that pushes every high-severity alert — level 13 and above on Wazuh — straight to a chat channel the moment it fires. Each message carries the rule, the agent, the time and, for a network alert, the source. Triage starts from a phone instead of from someone noticing a red number later.

It de-duplicates so a noisy rule can’t flood the channel, and it checks that each message was actually delivered rather than assuming it was.

Client work

Booth operations system for Ezforge

Built for a client, live and in daily use

Ezforge run retail booths at shopping centres. The owner was tracking sales, staff rosters and pay by hand across several booths at once, so I built her a web application that runs the whole operation in one place. It has been live since September 2026 and she uses it to run the business.

It runs on Cloudflare Workers with a D1 database and R2 for files. I wrote the front end as plain JavaScript compiled into a single page, with the pay engine, permissions and activity log enforced on the server. It covers the roster calendar, daily sales per booth, a payroll engine that follows the company’s own pay rules, rental agreements and invoices, importers for her real spreadsheets, and PDF payslips. It is backed by a test suite so I can change her pay rules without breaking last month’s payroll.

The system holds a client’s staff and payroll data, so it isn’t linked here. The screenshot is its demo mode, with no real data.
