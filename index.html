Running in production Flagship

Enterprise SOC Build-out

In August 2025 my employer was hit by ransomware. There was no central logging, so nobody could reconstruct what had happened or when. I proposed a Security Operations Centre, got approval from the Head of IT, and built it — from a proof of concept on a spare desktop to the production stack that now runs the company’s monitoring. I am the only person on security, so the architecture, the detection content, the incident response and the reporting are all mine.

  • Wazuh SIEM with co-located OpenSearch An all-in-one deployment on a Proxmox host I set up myself in the office, tuned at the systemd level to stay stable under sustained ingest.
  • Six log sources, one pipeline Firewall, core switching, wireless access points, Windows endpoints, Active Directory and a Zeek network sensor, normalised through custom ingest pipelines that resolve field-mapping conflicts between sources.
  • A sensor that sees the network, not a slice of it Port mirroring from the core and access switches feeds a multi-node Zeek cluster through a Python decapsulation stage, so internal traffic the firewall never sees is still on the wire for detection.
  • Detection content written for this network Custom decoders and correlation rules matched to the hardware actually in use, deliberately built without an endpoint-agent dependency I have no authority to deploy.
  • Alerts that reach someone A de-duplicated bot pushes critical alerts to chat, so triage does not depend on somebody having the dashboard open at the time.
  • The unglamorous half Retention policies and a purge job after archive logging filled the disk and silently flipped every index read-only; SQLite recovery across dozens of corrupt agent databases; NIC-level fixes for link flapping and transmit-engine hangs on the host.

01 Purple team

Purple Team — Both Chairs

I ran the red side and the blue side of the same exercise: a command-and-control listener reached through a tunnelling service, with implants beaconing on a fixed interval, then caught from the SIEM alone.

  • Red: a C2 listener on Kali Purple, exposed through a tunnel, with implants polling on a fixed interval
  • Blue: watched the same activity land in Wazuh, then wrote the detection rules for that signature
  • Proved the architecture from data — the tunnel launders the destination, so only DNS-resolution rules identified the actual internal victims
  • The findings mattered more than the catch: an unmonitored egress path, a beacon rule false-positiving on a vendor cloud, and remote-access tooling running with no authorization on record
  • Then tested it honestly: a plain implant to a clean host on 443 was missed, because the tunnel was itself the signature and a bare beacon has none

03 Collection

Zeek Network Security Monitoring Pipeline

A Zeek sensor fed by a core-switch traffic mirror, giving the SOC visibility into internal traffic the firewall never sees.

  • Custom Python stage strips encapsulation headers from mirrored traffic and injects it into a virtual capture interface
  • Multi-node ZeekControl cluster: logger, manager, proxy, and workers
  • Decoders classify each log stream by fields unique to that stream instead of guessing from field presence, with enrichment for direction and disposition
  • Detections for domain-generation bursts, DNS tunnelling, exfiltration and inbound scans
  • Correctly re-characterised an alarming reported capture loss as an MTU artefact of the mirror tunnel, not real packet loss — which decides exactly which detections you are allowed to trust
Zeek Python Traffic Mirroring NSM

SOC Visualization Suite

I built the tool I use every day. Two single-file consoles served from the SOC host: a global traffic map and an endpoint alert console. Writing them changed how I think about what an operator actually needs on screen.

04 — Background

About

I am a final-year Cybersecurity student at Asia Pacific University, and I run security operations for Palmgold Management, a licensed gaming operator in Malaysia. It has been the steepest learning curve I have had so far.

The ransomware incident in August 2025 is what shaped the work. Afterwards, nobody could answer the first question anyone asks: what happened, and when. There were no central logs to check. Everything I have built since comes back to that — getting the telemetry in, making it queryable, and putting it somewhere an analyst will actually look.

The habit I picked up from doing it alone is distrust of surface signals. A rule that loads is not a rule that works. A clean service start does not mean your rules loaded. A bulk request that reports success does not mean the documents were indexed. I have been caught by each of those, so now I check the artefact rather than the message about the artefact — and I have found more real problems that way than from any alert.

Running both sides of a purple-team exercise changed how I write detections. Being the attacker for a week taught me more about what a rule needs to catch than any template did, and the most useful thing to come out of it was not the catch — it was discovering a segment whose egress the sensor could not see at all. No rule helps on traffic you never collect.

Next I want to take the SOC from detection into response: automated blocking and host isolation through firewall and switch APIs, and interval-regularity analysis for beaconing that a rule engine cannot express. I am also looking for a team where I can learn from people who have run this at a larger scale.

Thanks are owed to Hong Yaw Lim, my senior in the IT department, who taught me an enormous amount of general IT knowledge. The colleagues here are genuinely some of the nicest people I have worked with, and that matters more than any stack.
